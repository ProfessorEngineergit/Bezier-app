# @bezier/core

This is the product. Everything else in the repo is a dependency or a
presentation of what happens here.

The kernel makes solids. The solver places lines. Neither has any idea what a
*design* is, that you extruded a sketch, then rounded an edge, then hollowed it
out, and that changing the first number should update all three. That memory, and
making it survive editing, is this package.

No DOM, no Three.js, no React. It runs in plain Node and is fully unit-testable,

## The two jobs

### 1. The feature graph

A document is not a solid. It is an ordered list of *what the user did*:

```
1. Sketch on XY      a 40 × 60 rectangle
2. Extrude           15 mm
3. Fillet            edges [...] at 3 mm
4. Shell             remove top face, 2 mm walls
```

Replaying that list produces the solid. Change `15` to `20` and replay, that is
what "parametric" means. It is also why documents are kilobytes instead of
megabytes, and why they survive kernel upgrades. See
[ADR 0005](../../docs/adr/0005-local-first-storage.md).

### 2. Stable geometry references: the hard problem

Read this part carefully; it is the whole differentiator.

In step 3 above, the user picked some edges. How did we record *which* edges?

The obvious answer is to store the kernel's edge numbers. This fails immediately.
When you change 15 mm to 20 mm, the kernel rebuilds from scratch and hands back a
solid with entirely fresh internal numbering. Edge #7 is now somewhere else
entirely. Your fillet lands on the wrong edge, or the rebuild fails, or, worst -
it silently produces a subtly wrong part.

This is the topological naming problem, and the reason "my model exploded when I
changed a dimension" is a familiar complaint about parametric CAD. It is hard, and
most of this package exists to solve it.

### How we attack it

Not by storing kernel ids, but by naming geometry after **the operation that
created it**:

- A face is named by the feature that produced it plus a tag identifying which
  face of that feature it is: *"the face generated by `extrude-1`, side 3"*. That
  name means the same thing before and after a rebuild, because it describes
  provenance rather than position.
- An edge is named as the intersection of its two adjacent faces. If both
  faces still have names, the edge between them does too.
- A vertex is named by the set of faces meeting at it.

Deriving edges and vertices this way is not an aesthetic choice, the kernel
tracks *faces only* (see `EvolutionData` in `@bezier/kernel`), so it is the only
material we have.

Threading names through a rebuild uses the kernel's report of which faces each
operation modified, generated, and deleted. Follow that chain from the first
feature to the last and a name assigned in step 2 can still be resolved in step 4.

### Why not just use the kernel's own face ids

Because they are not identities. Measured, not assumed
(`tools/spikes/face-hash-stability.ts`):

- rebuilding the same box in the same session preserves 0 of 6 hashes
- changing one box dimension leaves only 1 of 6 faces with unchanged geometry

The first kills the obvious approach. The second kills the obvious fallback -
matching faces by their geometry, because geometry moving under you is not an
edge case, it is what parametric modelling is.

So provenance is the only thing left that can carry identity, which is why the
naming scheme above is built on it. Signature remains useful for one narrow job:
telling apart siblings that share a provenance name.

Worth reading for background: FreeCAD's `ElementMap` and `ComplexGeoData` design.
Study the design; do not copy the code.

## Layout

```
src/
  stable-ref.ts   naming geometry so it survives edits  ← implemented, tested
  features.ts     the feature vocabulary                ← types only
  document.ts     the document model                    ← types only
  index.ts        public surface
```

`stable-ref.ts` is real, working, tested code. It is pure logic with no kernel
dependency, which makes it both the best place to start reading and a good place
to contribute, the naming *scheme* can be built and tested long before there is a
kernel to apply it to.
